# Задачи по доработке репозитория coursework-master

## 1. Адаптация UI под мобильные устройства (full-screen)

Сделать веб-интерфейс (`web/src/styles.css`, `web/src/pages/ChatPage.jsx`, `AuthPage.jsx`) адаптивным для мобильных экранов:
- Контейнер чата (`.page`, `.chat-container`) должен занимать 100% ширины и высоты вьюпорта на мобильных (сейчас, судя по всему, фиксированная/десктопная вёрстка на 145 строках CSS без медиа-запросов).
- Поле ввода и кнопка "Отправить" должны быть зафиксированы снизу экрана и не перекрываться клавиатурой на iOS/Android.
- Область сообщений (`.messages`) — скроллится независимо, с автоскроллом к последнему сообщению.
- Кнопки "Выйти" и "Инициализировать эмбеддинги" — не должны налезать на заголовок на узких экранах; возможно, вынести в компактное меню/иконки.
- Добавить `viewport-fit=cover` и учесть safe-area-insets (челка/навигационная панель) в `index.html` и CSS.
- Проверить на ширинах ~360–430px (типичные телефоны).

## 2. Доработка создания чата с выбором режима PLAIN/RAG

Сейчас в `web/src/api/chat.js` функция `createConversation()` жёстко отправляет `mode: 'PLAIN'`. Нужно:
- Дать пользователю выбрать режим (PLAIN/RAG) **до или в момент** создания диалога, а не только переключать его потом через `updateMode`.
- Передавать выбранный режим в `createConversation(mode)` вместо хардкода.
- Убедиться, что UI (`ChatPage.jsx`) корректно синхронизирует выбранный режим с состоянием на бэкенде сразу при старте, а не только при явном клике по радиокнопке.
- Проверить поведение бэкенда (java-service, эндпоинт `POST /api/conversations`) — принимает ли он `mode` в теле запроса на создание (сейчас видно, что `mode` есть в payload, но нужно свериться со Swagger/контроллером).

- Единая цветовая палитра и типографика (сейчас, судя по объёму CSS в 145 строк, стилизация минимальная).

### Опциональные подпункты (по возможности реализации)

**3.1. Видимая область "Thinking" (рассуждений модели)**

Сделать блок, как у ChatGPT/Claude/Gemini, который показывает промежуточные "размышления" модели отдельно от финального ответа, сворачиваемый/разворачиваемый.
- ⚠️ Ограничение: текущий пайплайн (`python-service/app/services/llm_client.py`, `create_chat_completion`) вызывает LLM через обычный `chat.completions.create` и возвращает только `response.choices[0].message.content` — reasoning-трейс не запрашивается и не прокидывается. Реализация зависит от того, поддерживает ли используемая модель (`LLM_MODEL` в `.env`, сейчас `gemini-3.5-flash`) режим "thinking"/"reasoning" в API и отдаёт ли его отдельным полем.
- Если модель это поддерживает: нужно (а) на бэкенде запрашивать и прокидывать reasoning-контент отдельным полем в `ChatResponse` (сейчас в `app/schemas.py` только `content`), прокинуть его через java-service до фронта; (б) на фронте — отдельный сворачиваемый блок над основным ответом в `MessageBubble.jsx`.
- Если модель не поддерживает — пункт помечается как невыполнимый технически и не делается (это и есть смысл пометки "опционально").

**3.2. Индикация этапов обработки RAG-запроса**

Показывать пользователю live-статус прохождения запроса вместо единого "Загрузка...", например: "Эмбеддим запрос…" → "Ищем похожие фрагменты в базе…" → "Формируем ответ…" → готовый ответ.
- Нужен потоковый канал между фронтом и бэкендом (Server-Sent Events или WebSocket), так как сейчас `POST /api/conversations/{id}/messages` — обычный синхронный REST-запрос, отдающий один финальный JSON-ответ (`ChatPage.jsx`, `api/chat.js: sendMessage`).
- На бэкенде (java-service) нужно эмитить промежуточные события по мере прохождения этапов: embedding запроса → поиск в pgvector → получение чанков → вызов LLM → ответ.
- На фронте — подписаться на этот стрим и обновлять статус-строку в реальном времени (заменить статичный `retrievalStatus` на пошаговый индикатор).
- Работает только в режиме RAG (в PLAIN этих этапов физически нет — там сразу идёт вызов LLM).

**3.3. Разделение истории чатов PLAIN и RAG**

Сейчас режим (`mode`) — это поле у одного и того же диалога (`conversationId`), то есть переключение PLAIN↔RAG происходит **внутри одной и той же истории сообщений** — не разделяет их физически.

Нужно:
- Дать пользователю создавать несколько независимых диалогов за одну сессию (сейчас `ChatPage.jsx` при старте либо восстанавливает единственный `conversationId` из `localStorage`, либо создаёт один новый — списка диалогов нет вообще).
- Добавить UI со списком чатов (сайдбар/выпадающий список), кнопку "Новый чат" с выбором режима (см. пункт 2), переключение между существующими чатами.
- При создании каждого чата режим (PLAIN или RAG) фиксируется на весь диалог, и в списке сообщений этого диалога не должны появляться сообщения из чатов другого режима — по факту это уже разделено на уровне `conversationId` в БД (java-service), но фронт должен явно давать доступ ко всем диалогам пользователя, а не только к одному сохранённому.
- Нужен эндпоинт на бэкенде "получить список диалогов пользователя" (`GET /api/conversations`) — уточнить, есть ли он уже на java-service или нужно добавить.

**3.4. Дефолтовая "память" бота — полная история с обрезкой при переполнении**

Реализовать самый простой вариант контекстной памяти:
- Каждый новый запрос к LLM включает **всю** историю сообщений текущего диалога (не только последнее сообщение) — проверить, что `python-service/app/routers/chat.py` (`req.messages`) и вызывающий код на java-service уже так делают, либо это нужно добавить.
- При достижении лимита (лимит токенов модели или заданный порог количества сообщений/символов — нужно выбрать конкретное число) — обрезать **старую половину** истории (например, оставить только последние N/2 сообщений), простое FIFO-усечение без суммаризации.
- Системное сообщение с RAG-контекстом (см. `chat.py`, `system_message` с найденными чанками) при обрезке не должно теряться — оно формируется заново на каждый запрос, это не часть истории, которую обрезают.
- Указать конкретный порог (например: если суммарная история превышает N сообщений или ~X токенов — обрезать до половины) как часть реализации, а не оставлять на усмотрение LLM в рантайме.

## 4. Тестовый набор для RAG

Нужен не просто unit-тест кода, а **eval-набор для качества RAG**-ответов:
- Набор тестовых вопросов с эталонными (ожидаемыми) ответами или ожидаемыми фрагментами контекста, которые должны быть найдены (`retrievedChunksCount > 0`, релевантность найденных чанков).
- Тесты должны проверять оба режима: PLAIN (без контекста) и RAG (с контекстом из базы) — на одинаковых вопросах, чтобы видеть разницу.
- Технически: где именно писать тесты — в `python-service` (retrieval/embedding логика, `app/services`, `app/routers/embed.py`, `app/routers/chat.py`) через pytest, и/или в `java-service` (контроллеры `conversations`) через JUnit.
- Нужны фикстуры с тестовыми данными для эмбеддингов — сверить с `java-service/src/main/resources/db/changelog/changes/002-seed-test-data.sql` и `003-embedding-3072.sql` — возможно, тестовый набор должен использовать этот сид.
- Указать метрику оценки (например: доля вопросов, где найден релевантный чанк; simple exact/contains-match по ключевым словам в ответе), т.к. точное сравнение текста LLM-ответа нестабильно.
