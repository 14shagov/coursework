# CI/CD: как это работает

Документ описывает автоматический деплой проекта на VPS: что происходит после `git push`,
какие компоненты участвуют, где что настроено и как разбираться, если сломалось.

Читать можно с нуля — предварительных знаний о GitHub Actions не требуется.

---

## 1. Что было и что стало

**Раньше** деплой был ручным. Нужно было зайти на сервер по SSH и выполнить:

```bash
git pull
docker compose build
docker compose up -d
```

Проблема не в трёх командах, а в том, что `docker compose build` собирал образы **на сервере**.
Сборка java-сервиса — это Maven, который скачивает зависимости и компилирует проект: минуты
работы CPU и сотни мегабайт памяти на машине, которая должна просто обслуживать запросы.
Плюс сборка шла каждый раз для всех сервисов, даже если менялся один файл в одном из них.

**Теперь** сборка происходит на серверах GitHub, а на VPS приезжают готовые образы. Пуш в
`master` — и через несколько минут в продакшене работает новая версия. Собирается только тот
сервис, в папке которого реально были изменения.

## 2. Общая схема

```
   ты                GitHub Actions              GHCR                    VPS
   │                       │                       │                      │
   ├─ git push master ──►  │                       │                      │
   │                       │                       │                      │
   │                  ┌────┴────┐                  │                      │
   │                  │ changes │ какие папки      │                      │
   │                  └────┬────┘ изменились?      │                      │
   │                       │                       │                      │
   │                  ┌────┴────┐                  │                      │
   │                  │  build  │ ─── docker push ──►                     │
   │                  └────┬────┘  (только изменившиеся образы)           │
   │                       │                       │                      │
   │                  ┌────┴────┐                  │                      │
   │                  │ deploy  │ ─── ssh ─────────────────────────────►  │
   │                  └─────────┘                  │                      │
   │                                               │   git pull           │
   │                                               ◄── docker compose pull│
   │                                               │   docker compose up -d
```

Три участника:

**GitHub Actions** — среда, где выполняется сборка. Бесплатные виртуальные машины, которые
поднимаются под каждую задачу и удаляются после. Всё, что они делают, описано в файле
[.github/workflows/deploy.yml](.github/workflows/deploy.yml).

**GHCR** (GitHub Container Registry, `ghcr.io`) — реестр Docker-образов, встроенный в GitHub.
Хранит собранные образы. Здесь лежат три пакета:

- `ghcr.io/14shagov/coursework-python-service:latest`
- `ghcr.io/14shagov/coursework-java-service:latest`
- `ghcr.io/14shagov/coursework-web:latest`

Все три публичные, поэтому сервер скачивает их без авторизации.

**VPS** — сервер, где всё запущено. Проект лежит в `/opt/coursework`, владелец — пользователь
`deploy`. Он же принимает SSH-подключение от GitHub Actions.

## 3. Разбор workflow

Файл [.github/workflows/deploy.yml](.github/workflows/deploy.yml). Разберём по частям.

### 3.1. Когда запускается

```yaml
on:
  push:
    branches: [master]
  workflow_dispatch:
```

`push` — автоматически при пуше в `master`. Ветка именно `master`, а не `main`: в этом
репозитории основная ветка называется так.

`workflow_dispatch` — кнопка ручного запуска в интерфейсе GitHub (Actions → Deploy → Run
workflow). Нужна для двух случаев: первый запуск, когда в реестре ещё нет ни одного образа, и
принудительная пересборка всего.

### 3.2. Права

```yaml
permissions:
  contents: read
  packages: write
```

Каждый запуск workflow получает временный токен `GITHUB_TOKEN`, живущий только пока идёт
задача. Здесь мы явно ограничиваем его: читать репозиторий и писать в реестр пакетов. Отдельный
персональный токен для GHCR не нужен — этого достаточно.

### 3.3. Имя образа

```yaml
env:
  IMAGE_PREFIX: ghcr.io/14shagov/coursework
```

К префиксу дописывается имя сервиса, получается `ghcr.io/14shagov/coursework-java-service`.
Значение записано литералом, а не собрано из переменных GitHub, по одной причине: GHCR требует
имена в нижнем регистре, а в выражениях Actions нет функции приведения регистра.

**Важно:** это значение должно совпадать с `image:` в [docker-compose.yml](docker-compose.yml).
Меняешь в одном месте — меняй во втором, иначе сервер будет тянуть не тот образ.

### 3.4. Job `changes` — кто изменился

```yaml
- uses: dorny/paths-filter@v3
  id: filter
  with:
    filters: |
      python-service:
        - 'python-service/**'
      java-service:
        - 'java-service/**'
      web:
        - 'web/**'
```

Это готовое действие сравнивает текущий коммит с предыдущим и говорит, какие из перечисленных
наборов путей затронуты. При событии `push` базой сравнения служит коммит до пуша, то есть
ответ буквально «что изменилось этим пушем».

Ключи фильтров (`python-service`, `java-service`, `web`) выбраны не случайно: они одновременно
совпадают с именами папок, именами сервисов в compose и суффиксами имён образов. Благодаря
этому промежуточной таблицы соответствий нигде нет.

Результат — JSON-массив, например `["python-service"]` или `["java-service","web"]`.

Дальше идёт шаг, который подменяет этот результат при ручном запуске:

```yaml
- id: pick
  env:
    CHANGED: ${{ steps.filter.outputs.changes }}
  run: |
    if [ "${{ github.event_name }}" = "workflow_dispatch" ]; then
      echo 'services=["python-service","java-service","web"]' >> "$GITHUB_OUTPUT"
    else
      echo "services=$CHANGED" >> "$GITHUB_OUTPUT"
    fi
```

При ручном запуске возвращается полный список — иначе фильтр сравнивал бы коммит сам с собой и
не нашёл изменений.

Запись в `$GITHUB_OUTPUT` — стандартный способ передать значение из одного job в другой.

### 3.4.1. Сервис `web` — особый случай

Два первых сервиса собираются из Dockerfile, которые существовали и до CI. Фронтенд появился
позже, и его сборка устроена иначе — [web/Dockerfile](web/Dockerfile):

```dockerfile
FROM node:22-alpine AS build
...
RUN npm run build

FROM nginx:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /build/dist /usr/share/nginx/html
```

Первый этап собирает статику через Vite, второй кладёт её в nginx. В финальном образе нет ни
Node, ни исходников — только готовые файлы и веб-сервер.

В режиме разработки Vite сам проксирует `/api` на `http://localhost:8080` (см.
[web/vite.config.js](web/vite.config.js)). В собранном виде dev-сервера нет, поэтому ту же роль
берёт nginx — [web/nginx.conf](web/nginx.conf):

```nginx
location /api/ {
    resolver 127.0.0.11 valid=10s;
    set $upstream java-service:8080;
    proxy_pass http://$upstream;
}
```

Нижний блок делает человека автором, верхний — модель, но подпись сквозная: обе части подписаны Игорем Карасевым как создателем. Если написать
`proxy_pass http://java-service:8080` напрямую, nginx резолвит имя **один раз при старте** и
кэширует IP навсегда. А наш деплой пересоздаёт только изменившиеся контейнеры — то есть
java-service может получить новый адрес, пока web продолжает работать со старым, и фронтенд
начнёт отдавать 502 до ручного перезапуска. Вынос имени в переменную плюс встроенный DNS Docker
(`127.0.0.11`) заставляет nginx резолвить адрес на каждый запрос. Побочный плюс: контейнер
стартует, даже если java-service в этот момент недоступен.

Вторая неочевидная строка в том же блоке:

```nginx
proxy_set_header Origin "";
```

Она решает проблему, которая иначе проявляется как «интерфейс открывается, но регистрация
отдаёт 403». Причина: браузер присылает заголовок `Origin` при любом методе кроме GET и HEAD —
**в том числе** когда запрос идёт на тот же самый адрес, откуда загружена страница. Spring видит
заголовок, считает запрос кросс-доменным и сверяет его со списком из `WebCorsConfig.java`. Адреса
в списке нет — ответ `403 Invalid CORS request`, причём в логе java-сервиса не появляется вообще
ничего, потому что отказ выдаёт фильтр до контроллера.

Держать список адресов в актуальном состоянии — путь в тупик: каждый новый способ открыть
интерфейс (тоннель, IP сервера, домен) требовал бы дописывать туда очередную строку. Вместо этого
заголовок снимается на прокси. Запрос, пришедший через nginx, по определению same-origin —
фронтенд отдал сам этот же nginx. Пустое значение заставляет nginx не передавать заголовок в
upstream совсем, Spring не видит признака кросс-доменности и пропускает запрос. Работает при
любом адресе в браузере, без настроек.

Безопасность от этого не страдает: авторизация построена на Bearer-токене из `localStorage`
(см. [web/src/api/client.js](web/src/api/client.js)), а не на cookie. Сторонний сайт не может
прочитать `localStorage` чужого origin, поэтому CORS в этой схеме от подделки запросов и не
защищал. При прямом обращении к java-сервису на 8080, минуя nginx, проверка продолжает работать
как раньше.

Проверить, что заголовок действительно снимается:

```bash
curl -s -o /dev/null -w 'через web: %{http_code}\n' -X POST http://localhost:8081/api/auth/register \
  -H 'Content-Type: application/json' -H 'Origin: http://example.invalid' \
  -d '{"username":"probe9","password":"probepass123"}'

curl -s -o /dev/null -w 'напрямую: %{http_code}\n' -X POST http://localhost:8080/api/auth/register \
  -H 'Content-Type: application/json' -H 'Origin: http://example.invalid' \
  -d '{"username":"probe10","password":"probepass123"}'
```

Ожидается `201` через web и `403` напрямую. Если через web тоже 403 — образ web не обновился.

### 3.5. Job `build` — сборка и публикация

```yaml
needs: changes
if: needs.changes.outputs.services != '[]'
strategy:
  fail-fast: false
  matrix:
    service: ${{ fromJSON(needs.changes.outputs.services) }}
```

`needs: changes` — ждать завершения предыдущего job.

`if` — не запускаться вовсе, если список пустой (например, изменился только README).

`matrix` — ключевой механизм. GitHub берёт массив и создаёт **по одной независимой задаче на
каждый элемент**, выполняя их параллельно. Изменились оба сервиса — собираются одновременно, а
не по очереди. Внутри задачи имя доступно как `${{ matrix.service }}`.

`fail-fast: false` — если java-сборка упала, python-сборка всё равно доводится до конца. По
умолчанию GitHub отменил бы вторую.

Шаги внутри:

```yaml
- uses: docker/login-action@v3
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

Авторизация в реестре встроенным токеном. `github.actor` — тот, кто инициировал запуск.

```yaml
- uses: docker/build-push-action@v6
  with:
    context: ./${{ matrix.service }}
    push: true
    tags: ${{ env.IMAGE_PREFIX }}-${{ matrix.service }}:latest
    cache-from: type=gha,scope=${{ matrix.service }}
    cache-to: type=gha,mode=max,scope=${{ matrix.service }}
    labels: org.opencontainers.image.source=${{ github.server_url }}/${{ github.repository }}
```

`context: ./python-service` — папка сборки. Dockerfile берётся оттуда же, никаких правок в сами
Dockerfile не вносилось, они те же, что и были.

`cache-from` / `cache-to` с `type=gha` — кэш слоёв в хранилище GitHub Actions. Без него каждая
сборка java-сервиса заново скачивала бы все Maven-зависимости.

`scope=${{ matrix.service }}` — **обязательный** параметр. Кэш GHA общий на репозиторий, и без
разделения по scope две параллельные сборки перезаписывали бы кэш друг друга.

`labels` с `org.opencontainers.image.source` — метка, по которой GitHub автоматически связывает
пакет в GHCR с этим репозиторием. Без неё пакет висел бы сам по себе.

### 3.6. Job `deploy` — доставка на сервер

```yaml
needs: [changes, build]
if: ${{ !cancelled() && needs.changes.result == 'success' && needs.build.result != 'failure' }}
```

Условие выглядит громоздко, но каждая часть нужна.

Если ни один сервис не изменился, job `build` вообще не запускался и получил статус `skipped`.
А `needs` по умолчанию требует `success` — то есть без явного `if` деплой молча не выполнился
бы. Поэтому проверяется не «успех», а «не провал»: `needs.build.result != 'failure'`.

`!cancelled()` — не выполняться, если запуск отменили вручную.

`needs.changes.result == 'success'` — если сломался сам определитель изменений, деплоить нечего.

Дальше настройка SSH:

```yaml
- name: Configure SSH
  env:
    SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
    SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}
  run: |
    install -d -m 700 ~/.ssh
    printf '%s\n' "$SSH_PRIVATE_KEY" > ~/.ssh/id_ed25519
    chmod 600 ~/.ssh/id_ed25519
    printf '%s\n' "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
    chmod 600 ~/.ssh/known_hosts
```

Сторонние SSH-действия из маркетплейса не используются: приватный ключ им передавать не нужно,
если всё делается четырьмя строками штатного `ssh`.

`known_hosts` берётся из секрета, а не отключается через `StrictHostKeyChecking=no`. Разница
принципиальная: с отключённой проверкой Actions доверился бы любому хосту, который ответит на
этот адрес, — то есть открыл бы возможность подмены. С зафиксированным ключом хоста подключение
к чужому серверу просто не состоится.

Сам деплой:

```yaml
run: |
  ssh -i ~/.ssh/id_ed25519 -p "$SSH_PORT" "$SSH_USER@$SSH_HOST" \
    "cd '$SSH_PROJECT_PATH' && git pull --ff-only && docker compose pull && docker compose up -d"
```

Три команды на сервере:

1. `git pull --ff-only` — обновить `docker-compose.yml` и остальные файлы репозитория. Флаг
   `--ff-only` запрещает автоматические merge-коммиты: если на сервере кто-то накоммитил
   локально, пул честно упадёт, а не создаст неожиданную историю.
2. `docker compose pull` — скачать образы из GHCR.
3. `docker compose up -d` — привести запущенные контейнеры в соответствие с конфигурацией.

## 4. Почему пересоздаётся только часть контейнеров

Это самая неочевидная часть схемы, и она держится не на нашей логике, а на встроенном
поведении Docker Compose.

Каждый образ идентифицируется **digest** — хешем содержимого. Тег `latest` это просто ссылка на
какой-то digest. Когда `docker compose pull` скачивает образ, он сравнивает digest в реестре с
тем, что уже есть локально. Затем `up -d` сравнивает digest образа с тем, на котором запущен
контейнер: совпадает — контейнер не трогается, различается — пересоздаётся.

Отсюда два следствия, которые стоит понимать.

**Деплой безопасно запускать вхолостую.** Если ничего не менялось, `up -d` ничего не сделает.
Именно поэтому deploy-job запускается даже когда сборки не было.

**Изменение файла не всегда означает новый образ.** Например, правка в `.dockerignore`
затрагивает папку `python-service/`, path-фильтр срабатывает, сборка запускается — но этот файл
никуда не копируется внутрь образа (`Dockerfile` берёт только `requirements.txt` и `app/`). Все
слои собираются из кэша побайтово прежними, digest получается тот же, и контейнер не
пересоздаётся. Это не сбой, а ровно то поведение, которого мы хотим.

Проверить, что именно произошло, можно по времени создания контейнеров:

```bash
docker ps --format '{{.Names}}\t{{.CreatedAt}}'
```

## 5. Секреты GitHub

Настраиваются в Settings → Secrets and variables → Actions. Внутри workflow доступны как
`${{ secrets.ИМЯ }}`, в логах автоматически маскируются.

| Секрет | Что содержит |
|---|---|
| `SSH_HOST` | IP или домен VPS |
| `SSH_USER` | `deploy` |
| `SSH_PORT` | порт SSH (у этого сервера нестандартный) |
| `SSH_PROJECT_PATH` | `/opt/coursework` |
| `SSH_PRIVATE_KEY` | приватный ключ `cwf_deploy` целиком, включая строки `-----BEGIN`/`-----END`, без пароля |
| `SSH_KNOWN_HOSTS` | публичный ключ хоста в формате `[адрес]:порт ssh-ed25519 AAAA...` |

Ни адрес сервера, ни путь к проекту не хранятся в файлах репозитория — он публичный, и
раскладке сервера там не место.

`GITHUB_TOKEN` в списке нет и создавать его не надо: он выдаётся автоматически каждому запуску.

## 6. Что настроено на сервере

**Пользователь `deploy`.** Не root. Входит в группу `docker`, что позволяет ему управлять
контейнерами без `sudo`.

Про это стоит знать честно: членство в группе `docker` фактически равносильно root на этой
машине — имея доступ к демону, можно смонтировать корень файловой системы в контейнер. Смысл
отдельного пользователя не в изоляции, а в том, что скомпрометированный ключ CI не даёт прямого
root-логина по SSH и отзывается удалением одной строки из `authorized_keys`.

**Каталог `/opt/coursework`.** Git-клон репозитория, владелец `deploy`. Все операции с ним нужно
выполнять от имени владельца:

```bash
sudo -u deploy git -C /opt/coursework pull --ff-only
```

Если запустить git под root, он откажется работать с сообщением `detected dubious ownership`.
Это защита, а не помеха: root создал бы в `.git` файлы, принадлежащие root, и следующий пул из
CI сломался бы по правам.

**Файл `.env`.** Лежит рядом с `docker-compose.yml`, в git не попадает. Compose подставляет из
него переменные. Шаблон — [.env.example](.env.example).

Обязательные переменные записаны как `${VAR:?}`: если значение отсутствует или пусто, compose
**отказывается** запускаться с внятным сообщением. Это сделано намеренно. Раньше там стояли
дефолты от GitHub Models, и при потерянном `.env` сервис не падал, а тихо уходил на чужого
провайдера — искать причину пришлось бы по невнятным 401.

**Compose V2.** Плагин лежит в `/usr/local/lib/docker/cli-plugins/docker-compose` и вызывается
как `docker compose` (без дефиса). Старый `docker-compose` 1.29 в системе тоже есть, но он не
понимает текущий формат файла и в деплое не участвует.

**Соседний проект.** На том же демоне работают контейнеры `skuf-bot-prod` и
`skuf-postgres-prod`, не имеющие отношения к этому проекту. Отсюда важное ограничение: **никогда
не запускать** на этом сервере `docker image prune -a` или `docker system prune` — они удалят
образы соседнего проекта, и он не поднимется после следующего рестарта. Обычный
`docker image prune -f` безопасен: он трогает только образы без тегов.

**Порты.** В обычном режиме ни один порт проекта не открыт в интернет. Все публикации привязаны
к loopback:

| Что | Адрес на сервере | Назначение |
|---|---|---|
| web (nginx) | `127.0.0.1:8081` | веб-интерфейс, он же прокси на API |
| java-service | `127.0.0.1:8080` | REST API, swagger |
| python-service | `127.0.0.1:8000` | внутренний сервис для RAG и обращений к LLM |
| postgres | `127.0.0.1:5432` | база |

Обращаться к ним извне можно через SSH-тоннель (раздел 7). Временное исключение — демонстрация
проекта: overlay `docker-compose.demo.yml` добавляет `web` публикацию `0.0.0.0:80`, тоже
описано в разделе 7. Все остальные порты остаются на loopback и в этом режиме.

Постоянно открытым наружу не держится ничего, и это осознанный выбор: пока ключ подписи JWT не
заменён на собственный (см. раздел 9), открытый 8080 означал бы возможность войти под любым
пользователем.

Проверить, что снаружи действительно закрыто, можно с любой другой машины:

```bash
Test-NetConnection адрес-сервера -Port 8080
```

`TcpTestSucceeded : False` при `PingSucceeded : True` — то, что нужно: хост жив, порт закрыт.

## 7. Повседневные сценарии

### Выкатить изменение

```bash
git add -A && git commit -m "описание" && git push
```

Всё. Через несколько минут изменения в продакшене. Наблюдать за процессом — вкладка Actions.

### Пересобрать всё принудительно

Actions → Deploy → Run workflow. Нужно, если образ повредился, если менялся базовый образ в
`Dockerfile`, или если хочется убедиться, что сборка с нуля проходит.

### Изменить переменную окружения

Правки в `.env` делаются на сервере руками — файл не в репозитории:

```bash
sudo -u deploy nano /opt/coursework/.env
sudo -u deploy docker compose -f /opt/coursework/docker-compose.yml up -d
```

Пересборка образов при этом не нужна: переменные передаются в контейнер при запуске, а не
запекаются в образ.

### Открыть приложение со своего компьютера

Порты закрыты снаружи, доступ идёт через SSH-тоннель. В отдельном окне PowerShell:

```bash
ssh -N -i "$env:USERPROFILE\.ssh\cwf_deploy" -p ПОРТ -L 8081:127.0.0.1:8081 -L 8080:127.0.0.1:8080 deploy@АДРЕС
```

`-N` означает «не выполнять команд, только форвардить». Окно висит без вывода, это нормально;
закрытие окна рвёт тоннель.

Пока тоннель поднят:

| Адрес у себя | Что откроется |
|---|---|
| `http://localhost:8081` | веб-интерфейс, production-сборка — та же, что увидят пользователи |
| `http://localhost:8080/swagger-ui.html` | swagger java-сервиса |
| `http://localhost:8080/v3/api-docs` | OpenAPI-схема в JSON |

Регистрация нового пользователя ограничена валидацией из `RegisterRequest.java`: username от 3
символов, пароль от 8.

Проверка только API, без интерфейса:

```bash
curl -X POST http://localhost:8080/api/auth/register -H "Content-Type: application/json" -d '{"username":"testuser","password":"testpass123"}'
```

Ответ 201 с токеном означает, что java-service, база и схема liquibase в порядке. Чат — самая
показательная проверка: он единственный задействует всю цепочку до LLM.

### Открыть проект в интернет на время

Обычно наружу не смотрит ничего. Чтобы показать проект с любого компьютера, есть overlay-файл
[docker-compose.demo.yml](docker-compose.demo.yml) — он состоит из четырёх строк и меняет
ровно одну вещь: публикацию порта у сервиса `web`.

**Открыть:**

```bash
cd /opt/coursework && sudo -u deploy docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d web
```

**Закрыть:**

```bash
cd /opt/coursework && sudo -u deploy docker compose up -d web
```

Адрес — `http://АДРЕС-СЕРВЕРА`, без номера порта и **без `https`**. Порт 80 в URL не пишется,
потому что он для HTTP дефолтный. `https` не заработает: TLS-сертификата в этой схеме нет ни у
одного компонента.

Дальше — почему это работает именно так.

**Почему вторая команда закрывает, а не просто запускает.** `docker compose up -d` — не команда
запуска, а команда сверки. Compose вычисляет конфигурацию из переданных файлов, сравнивает с тем,
что реально запущено, и пересоздаёт только те контейнеры, у которых конфигурация разошлась.
Остальные оставляет как есть — в выводе они помечены `Running`. Поэтому вторая команда, где
overlay не указан, видит желаемую публикацию `127.0.0.1:8081` вместо фактических
`127.0.0.1:8081` плюс `0.0.0.0:80` и пересоздаёт `web` обратно. Postgres, python-service и
java-service при переключении в любую сторону не трогаются вообще.

Смена занимает около двух секунд: nginx стартует мгновенно, ничего не компилируется и не
скачивается.

**Где на самом деле находится «замок».** Не в файрволе, а в том, на каком адресе слушает сокет.
Публикация `127.0.0.1:8081:80` означает, что Docker пробрасывает порт только на loopback — с
внешнего интерфейса этого порта физически не существует, поэтому и блокировать нечего. Overlay
добавляет вторую публикацию, `80:80` без указания адреса, что равносильно `0.0.0.0:80` — вот она
и делает проект доступным извне.

**Почему `iptables -A INPUT --dport 80 -j DROP` порт не закроет.** Это важная деталь, потому что
интуиция подсказывает обратное. Пакет, адресованный опубликованному порту, сначала проходит DNAT
в цепочке `nat/PREROUTING`, где адресат подменяется на IP контейнера. После этого пакет
маршрутизируется в контейнер и идёт по цепочке `FORWARD` — там Docker держит свою `DOCKER-USER`.
Цепочку `INPUT` он не проходит совсем, потому что предназначен не самому хосту. Правило в `INPUT`
будет молча игнорироваться, и порт останется открытым при полной уверенности, что он закрыт.
Та же причина, по которой `ufw` не управляет портами контейнеров (см. раздел 6).

**Почему тоннель продолжает работать во время демо.** Списки портов в compose при наложении
файлов не заменяются, а складываются. Поэтому в открытом режиме у `web` две публикации сразу:
`127.0.0.1:8081` и `0.0.0.0:80`. Первая — для SSH-тоннеля, вторая — для гостей. Проверить можно
так:

```bash
docker compose -f docker-compose.yml -f docker-compose.demo.yml config | grep -A3 'published'
```

**Почему нельзя случайно оставить порт открытым надолго.** Workflow деплоит обычной командой
`docker compose up -d`, без overlay. По логике сверки это возвращает публикацию только на
loopback — то есть **следующая же выкатка закрывает порт сама**, даже если ты про него забыл.
Забыть в опасную сторону не получится, забыть можно только в безопасную.

**Проверка снаружи**, с другой машины, в обоих режимах:

```bash
Test-NetConnection АДРЕС-СЕРВЕРА -Port 80
```

`TcpTestSucceeded : True` в открытом режиме, `False` в закрытом.

**Что нужно учесть.** Порт 80 на хосте должен быть свободен — проверить `ss -tlnp | grep ':80\s'`.
Если настроен файрвол провайдера, порт 80 в нём нужно разрешить, иначе снаружи будет таймаут при
корректно открытой публикации. И трафик идёт открытым текстом: пароли при регистрации и
JWT-токены передаются как есть. Для учебного проекта без ценных данных это осознанный компромисс,
но помнить о нём стоит — особенно с учётом того, что ключ подписи JWT остался дефолтным
(см. раздел 9).

### Посмотреть логи

```bash
docker compose -f /opt/coursework/docker-compose.yml logs --tail=80 java-service
```

### Проверить, что всё живо

```bash
docker compose -f /opt/coursework/docker-compose.yml ps
curl -fsS -o /dev/null -w 'web    %{http_code}\n' localhost:8081/
curl -fsS -o /dev/null -w 'python %{http_code}\n' localhost:8000/docs
curl -fsS -o /dev/null -w 'java   %{http_code}\n' localhost:8080/v3/api-docs
```

Все три должны вернуть 200. Обращение к java по `/` вернёт 401 — это нормально, корень требует
аутентификации. Публичные пути перечислены в `SecurityConfig.java`: `/api/auth/**`,
`/swagger-ui/**`, `/v3/api-docs/**`.

## 8. Диагностика

Ошибки ниже — те, что реально встретились при настройке. Симптом → причина → проверка.

### `ssh-keyscan` возвращает `Connection refused`

SSH слушает не на 22 порту. Узнать фактический:

```bash
ss -tlnp | grep -i ssh
```

Найденный номер идёт и в `ssh-keyscan -p`, и в секрет `SSH_PORT`.

### `Permission denied (publickey)`

Три возможные причины, проверять в этом порядке.

**Содержимое `authorized_keys` не является публичным ключом.** Проверка:

```bash
ssh-keygen -lf /home/deploy/.ssh/authorized_keys
```

Ответ `is not a public key file` означает, что в файл попало что-то другое — например отпечаток
`SHA256:...` или строка из `ssh-keyscan` в формате known_hosts. Правильная строка состоит из
трёх полей и начинается с `ssh-ed25519`.

**Приватный ключ зашифрован.** Проверка:

```bash
ssh-keygen -y -f ~/.ssh/cwf_deploy
```

Если спрашивает пароль — CI ввести его не сможет. Снять:

```bash
ssh-keygen -p -f ~/.ssh/cwf_deploy
```

**Права на каталоги.** sshd отвергает ключ, если домашний каталог доступен на запись группе или
всем:

```bash
ls -ld /home/deploy /home/deploy/.ssh
```

Нужно `drwxr-xr-x` (или строже) на домашний и `drwx------` на `.ssh`.

Точную причину всегда пишет сам sshd:

```bash
journalctl -u ssh -u sshd -n 30 --no-pager
```

Строка `Failed publickey for deploy` означает, что ключ был предложен и отвергнут — дело в
содержимом файла или правах. Отсутствие такой строки означает, что клиент ключ вообще не
предложил — проблема на своей машине.

### `docker: 'compose' is not a docker command`

Не установлен плагин Compose V2. Проверять надо именно от имени `deploy`, потому что плагин
может стоять в домашнем каталоге root:

```bash
sudo -u deploy docker compose version
```

### Деплой падает на `docker compose pull`

Пакеты в GHCR приватные. GHCR делает их такими по умолчанию — видимость меняется один раз
вручную: профиль → Packages → пакет → Package settings → Change visibility → Public.

### `required variable ... is missing a value`

В `.env` на сервере нет одной из обязательных переменных. Список — в
[.env.example](.env.example). Проверка:

```bash
sudo -u deploy docker compose -f /opt/coursework/docker-compose.yml config >/dev/null && echo OK
```

### Workflow не запускается на пуш

Проверить, что ветка в `on.push.branches` совпадает с фактической. Здесь `master`.

### Сборка прошла, но контейнер не пересоздался

Скорее всего образ не изменился. См. раздел 4.

### Регистрация или вход отдают 403

Признаки: статика грузится нормально, `POST /api/...` отдаёт 403 с очень коротким телом, в логах
java-сервиса при этом **ничего** — отказ выдаёт CORS-фильтр до контроллера.

Через nginx этого быть не должно: он снимает заголовок `Origin` (см. раздел 3.4.1). Если 403
всё-таки приходит, значит образ web устарел и снятия заголовка в нём ещё нет. Проверка:

```bash
curl -s -o /dev/null -w 'через web: %{http_code}\n' -X POST http://localhost:8081/api/auth/register -H 'Content-Type: application/json' -H 'Origin: http://example.invalid' -d '{"username":"probe9","password":"probepass123"}'
curl -s -o /dev/null -w 'напрямую: %{http_code}\n' -X POST http://localhost:8080/api/auth/register -H 'Content-Type: application/json' -H 'Origin: http://example.invalid' -d '{"username":"probe10","password":"probepass123"}'
```

Норма — `201` через web и `403` напрямую: второй отказ ожидаем, там CORS работает штатно. Если
первый тоже 403 — подтянуть свежий образ:

```bash
cd /opt/coursework && sudo -u deploy docker compose pull web && sudo -u deploy docker compose up -d web
```

Если же обращение идёт **напрямую** к java-сервису, минуя nginx — например Vite в режиме
разработки на 5173 или запрос из swagger — то там список origin'ов действует. Лечится добавлением
адреса в `APP_CORS_ALLOWED_ORIGINS` в `.env` и перезапуском java-сервиса, пересборка образа не
нужна.

### Порт открыт overlay'ем, но снаружи не подключается

Сначала различить два симптома, они указывают на разное.

**Таймаут** — пакеты не доходят до хоста. Значит режет что-то между тобой и сервером: файрвол
провайдера или security group в панели VPS. Разрешить в нём порт 80.

**Connection refused** — хост ответил, но на порту никто не слушает. Значит overlay не применился.
Проверить фактические публикации:

```bash
docker port rag-web
```

Должны быть две строки: `80/tcp -> 127.0.0.1:8081` и `80/tcp -> 0.0.0.0:80`. Если второй нет —
команда запускалась без `-f docker-compose.demo.yml`, либо порт 80 на хосте занят кем-то ещё:

```bash
ss -tlnp | grep ':80\s'
```

Правила `iptables` в цепочке `INPUT` тут ни при чём в обе стороны — ни закрыть, ни открыть порт
контейнера они не могут, причина разобрана в разделе 7.

### Веб открывается, но все запросы отдают 502

nginx не может дойти до java-service. Проверить, что тот вообще жив:

```bash
docker compose -f /opt/coursework/docker-compose.yml ps java-service
docker compose -f /opt/coursework/docker-compose.yml logs --tail=50 web
```

В логах web будет видно, что именно не получилось у прокси. Если java-service поднят и отвечает
на `localhost:8080`, а через web всё равно 502 — перезапустить web:

```bash
sudo -u deploy docker compose -f /opt/coursework/docker-compose.yml restart web
```

### Тоннель поднят, но `localhost:8081` не открывается

Проверить, что тоннель действительно установлен: окно с `ssh -N` должно висеть без ошибок. Если
он оборвался, `-L` пробросы исчезают вместе с ним. Ещё вариант — порт 8081 уже занят на своей
машине чем-то другим; тогда пробросить на другой локальный номер:

```bash
ssh -N -i "$env:USERPROFILE\.ssh\cwf_deploy" -p ПОРТ -L 9081:127.0.0.1:8081 deploy@АДРЕС
```

И открывать `http://localhost:9081`.

## 9. Что сознательно не сделано

Каждый пункт — осознанный компромисс, а не забытая задача.

**Только тег `latest`, без версий по коммитам.** Простой вариант для старта. Цена: откатиться
на предыдущую версию можно только пересборкой старого коммита, готового образа для отката нет.
Добавлять, когда понадобится быстрый откат.

**Нет тестов в CI.** Сборка не запускает ни `mvn test`, ни `pytest`. Сломанный код доедет до
продакшена — workflow проверяет только то, что образ собирается.

**Нет проверки живости после `up -d`.** Деплой считается успешным по коду возврата команды, а не
по факту, что сервис ответил на запрос. Контейнер, падающий через две секунды после старта, даст
зелёный workflow.

**Ключ подписи JWT по умолчанию публичный.** В `docker-compose.yml` переменная
`APP_SECURITY_JWT_SECRET` передаётся в java-service, но её дефолт — то же значение, что лежит в
`application.yml` в открытом репозитории. Пока в `.env` не задано своё значение, обладатель этого
ключа может подписать валидный токен и войти под любым пользователем.

В обычном режиме риск ограничен периметром: порт 8080 закрыт снаружи. Но стоит понимать, что во
время демонстрации (раздел 7) это ограничение снимается — nginx проксирует `/api/` на
java-service, то есть по адресу `http://АДРЕС-СЕРВЕРА/api/...` API становится доступен из
интернета вместе с интерфейсом. Отдельный порт для этого открывать не нужно.

Закрывается так:

```bash
openssl rand -base64 48
```

Результат вписать в `.env` в `APP_SECURITY_JWT_SECRET` и перезапустить java-service. Побочный
эффект: все ранее выданные токены станут недействительны, пользователям придётся войти заново.

**Нет TLS и нет домена.** Постоянный доступ — только через SSH-тоннель, временный показ — через
overlay из раздела 7, и в обоих случаях это HTTP без шифрования. По голому IP обычный сертификат
получить нельзя: Let's Encrypt для IP-адресов их не выдаёт. Для учебного проекта решено, что
домен и TLS не нужны. Следующий шаг в эту сторону, если понадобится: домен плюс Caddy на 443, он
выпускает и продлевает сертификат сам, проксировать на `127.0.0.1:8081`.

**`desktop/` не контейнеризован.** Electron-обёртка запускается локально, к деплою отношения не
имеет.

**Postgres не собирается в CI.** Он берётся готовым образом `pgvector/pgvector:pg16`. CI трогает
только сервисы, у которых есть свой Dockerfile.
